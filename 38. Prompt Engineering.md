# Module 38: Prompt Engineering

## Overview

This module covers the practical foundations of prompt engineering for LLMs and agents. It explains why prompts are critical, the structure of an effective prompt, rules for writing better prompts, and how to debug and improve prompts iteratively.

---

## Why prompt engineering matters

- Prompts are the interface between you and the model.
- A good prompt can change the result dramatically.
- Prompting is not just about wording; it is about giving the model a clear work order.
- Professional use cases require precise, reliable prompts with minimal back-and-forth.

### Key idea

Think of a prompt as a work order for a very fast assistant: short, specific, and testable.

---

## Anatomy of a solid prompt

A strong prompt typically contains:

1. Role: define who the model is acting as.
   - Example: “You are a helpful assistant,” “You are a professional receptionist,” “You are a software developer.”
2. Task: state the exact action clearly.
   - Example: “Summarize the five bullet notes into three actions.”
3. Context: provide only what is necessary.
   - No extra personal details or irrelevant background.
4. Rules and constraints: specify style, length, format, and what to avoid.
   - Example: “Each action less than 12 words. No jargon. Use a spartan tone.”
5. Output format: tell the model exactly how you want results.
   - Structured output like JSON or bullet points makes results immediately usable.

### Prompt checklist

- Define role
- Define task
- Provide essential context
- Set rules and constraints
- Specify output format

---

## Rules for writing good prompts

### 1. Be specific about task and audience

- The model performs best when you define the task clearly.
- Also name the audience, tone, and required format.
- Example: don’t just ask for a report; ask for a report for a specific audience, length, and style.

### 2. Delimit the context

- Use separators and clean structure.
- Well-delimited context is easier for the model to understand.
- Avoid dumping long unstructured text.

### 3. Use one strong example

- Provide a compact, high-quality example of the desired output.
- One good example is better than many weak ones.
- Use multiple examples only when you need to show variation or edge cases.

### 4. Cut redundancy

- Remove unnecessary words from role and instructions.
- Redundant phrases reduce prompt efficiency.
- Example: “You are a technical analyst at Microsoft” is better than adding several redundant qualifiers.

### 5. Minimize prompt length while keeping meaning

- More tokens can weaken reasoning and increase cost.
- Good prompt engineering aims to get the best result with the least amount of input.

---

## Structured output is powerful

- Asking for a structure makes the model think in fields.
- JSON, bullet lists, tables, and clear sections are easiest to use downstream.
- Structured prompts help make outputs machine-usable and reduce ambiguity.

---

## Debugging and improving prompts

Prompt engineering is iterative.

### Iteration is normal

- You rarely get the perfect prompt on the first try.
- Test variations and refine based on output quality.
- Real applications often require multiple rounds of prompt tuning.

### 1. A/B test variations

- Compare two prompt versions side-by-side.
- Keep the one that gives better results.
- You can also compare models and settings in the same way.

### 2. Isolate variables

- Change one factor at a time.
- Example: change only the tone or only the role.
- This helps identify what actually improves output.

### 3. Maintain a golden set

- Keep a stable set of prompts and test inputs.
- Use the golden set to track improvement and regressions.
- Without it, it becomes hard to know which change caused a drop in quality.

### 4. Track performance against a rubric

Monitor metrics such as:

- Format correctness
- Completeness
- Accuracy
- Length
- Field coverage

### 5. Treat prompt tuning like mixing audio

- Adjust one knob at a time.
- Tune small parameters to find the best balance.
- The analogy is useful: each change should be deliberate and isolated.

---

## Practical prompt engineering advice

- Be authoritative, not polite.
- Do not over-explain or appeal to the model’s goodwill.
- Use concise, direct language.
- Keep prompts lean and avoid unnecessary context.
- Use strong examples when possible.

---

## Recommended workflow

1. Start with a clear role and task.
2. Add only necessary context.
3. Specify output format up front.
4. Test the first version.
5. Iterate with A/B tests.
6. Isolate changes.
7. Track results with a stable prompt dataset.
