## Overview

This module walks through building a local RAG workflow using the n8n Self Hosted AI Starter Kit. It shows how to use Quadrant as the local vector store, Ollama for embeddings and local model inference, and how to connect documents via n8n form trigger, vector ingestion, and chat/agent retrieval.

---

## Self-hosted local RAG stack

With the AI Starter Kit in place, the stack includes:

- n8n self-hosted instance on `localhost:5678`
- Quadrant local vector database
- Postgres as the backing database
- Ollama local model/embedding service
- Optional ngrok tunnel for external access

This forms a complete local RAG environment where data stays on your machine and the vector database is directly accessible from n8n.

---

## Building the document ingestion flow

The demo builds a flow using a **Form Trigger**:

1. Add a form trigger node for `on new form event`.
2. Configure form title and description (e.g. "Document upload" and "Please upload a PDF you want to add to our vector database").
3. Add a file element to the form, optionally restricting it to `.pdf`.
4. Execute the workflow and upload a PDF file.

### Why this is important

- A form trigger enables non-technical users to upload documents through a browser interface.
- The uploaded file arrives as **binary data** in n8n.
- Binary file handling is the first step to ingesting document content into the vector store.

---

## Document loader and vector store insertion

After the file upload:

1. Use the **default data loader** for binary input.
2. Set the data type to `binary`.
3. Connect the loader to a **local Quadrant vector store** node.
4. Name the collection and choose embedding batch size (demo used `200`).

The important flow is:

- File upload → binary content → data loader → Quadrant vector DB insert

This stores chunks and embeddings from the PDF into Quadrant.

---

## Embedding strategy and Ollama

Key points from the demo:

- Use the same embedding model for ingestion and retrieval.
- Ollama supports embedding models and local LLMs.
- In the demo, the instructor selects an Ollama embedding model such as `mQB AI M large` or `Nomic mtext`.
- The embedding model is downloaded inside the Ollama container with a command executed in Docker.
- This creates a fully local embedding pipeline: document → chunk → Ollama embedding → Quadrant vector store.

### Important distinction

- Ollama can act as a local embedding provider as well as a local LLM provider.
- Embeddings are not the same as LLM responses; the demo emphasizes that Ollama embeddings are a separate capability from the Ollama language model.

## Quadrant vector store visualization

The demo shows how Quadrant stores vector points and metadata:

- Collections hold chunks of data as points.
- Each point includes vector values, metadata, and content.
- Visualization displays the vector space and nearest neighbors.
- The demo confirms 53 points after ingestion of the PDF.

### Why visualization matters

- It helps you understand how the query embedding is mapped in vector space.
- A query lands near the nearest document points.
- The UI can show the five closest points by default.
- This confirms retrieval is working: similar vectors cluster near each other.

## The local query flow

The query process follows the same RAG pattern:

1. User sends a chat query.
2. Query is embedded using the same embedding model.
3. Quadrant searches for nearest vectors.
4. Retrieved chunks are passed to the LLM for answer generation.

The demo shows that when the query arrives, it matches nearby points and can produce a response grounded on the stored document content.

---

## Setting up the Quadrant agent tool

To create an agent:

1. Add a chat trigger node.
2. Add a tool configured as `Quadrant Vector Store`.
3. Provide a tool description such as "Please find the answer for the query.".
4. Select the correct Quadrant vector DB collection.
5. Set the limit (demo used `5`).
6. Use the same embedding provider for the tool.

### Critical detail

- If the embedding model used by the tool differs from ingestion, retrieval will fail or return bad matches.
- The demo highlights that mismatch causes the query point to land in the wrong region of vector space.

## Local chat model choices

The demo tests two options:

- Ollama local chat model (e.g., `llama-3.2`) for fully local inference.
- OpenAI chat model for fallback when the local model is too slow or not strong enough.

The instructor notes:

- A small local model can work but may be slow and less capable.
- OpenAI/GPT-4 can provide faster, higher-quality answers when local inference is insufficient.
- Local-only is valuable for privacy and data control, but may need a stronger model for production use.

---

## Prompting and tool use

The demo emphasizes prompt engineering:

- Instruct the assistant to use the Quadrant tool.
- Example guidance: "Make sure to help out the query by searching via Quadrant RAG tool.".
- Better prompt design improves the chance the agent uses the vector store correctly.

### Common failure mode

- The agent may not hit the Quadrant tool if the prompt is weak.
- If the agent does not use the tool, it may answer from its base model knowledge instead of the local document.
- This is why explicit instructions and tool naming are important.

---

## OpenAI fallback for answers

The demo switches to an OpenAI chat model when the local Ollama agent is too slow or returns poor quality:

- Configure OpenAI chat credentials in n8n.
- Select a stronger model such as `gpt-4o` or `GPT`.
- Use the same Quadrant tool and retrieval flow.

This layered setup shows a hybrid architecture:

- Local storage and embeddings remain local.
- The answer generation can use a remote strong model when needed.

## Troubleshooting and refinement

The transcript records real troubleshooting steps:

- Fix prompting when the tool is not hit.
- Ensure the query includes the correct reference to the paper and tool.
- Avoid adding memory incorrectly; extra memory entries can confuse the flow.
- If the agent returns non-specific answers, improve the prompt or increase the tool limit.
- Use simpler insert data flows and collections when testing.

---

## Important local RAG lessons

- Keep the vector store local for privacy and data control.
- Use a local embedding model if you want fully offline ingestion.
- Visualize the vector DB to verify point similarity and nearest neighbors.
- Build a clean tool/agent flow in n8n that explicitly references the local vector store.
- Use a stronger external model only as a fallback, not as the primary retrieval mechanism.
