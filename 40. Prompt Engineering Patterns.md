# Module 40: Prompt Engineering Patterns

## Overview

This module presents advanced prompt engineering patterns and recipes to make LLM output more predictable, reliable, and automation-ready. It covers role/persona, one-shot/few-shot learning, plan-then-answer, data extraction, routing/classification, hard-capped summarization, critique-and-revise, XML-tagged sections, and tool/function caller patterns.

---

## Universal prompt skeleton

Use this structure as your base:

- Role
- Task
- Context
- Rules
- Output format
- Examples

Pro tips:

- Use delimiters like `---` or XML-like tags to separate instructions from data.
- Prefer explicit schema-based output over free-form text.
- Define exact output fields even if you don’t need strict JSON.

---

## 1. Persona and role pattern

A clear role helps the model adopt the right voice and style.

- Define the persona and expertise.
  - Example: "You are a supportive triage assistant with five years of customer experience."
- Specify tone and audience.
  - Example: formal, casual, professional, executive.
- Add exact do’s and don’ts.
- Specify output fields and character limits.

### Key lesson

Role alone does not guarantee structure. Always specify exact output format with schemas or examples.

---

## 2. One-shot, few-shot, and many-shot learning

When format or style is hard to describe in words, teach by example.

- Use 1–3 high-signal examples that demonstrate the exact pattern you want.
- One strong example is better than many weak examples.
- Keep examples compact to avoid prompt bloat.
- Use negative examples when you want to show common mistakes.

### When to use this

- Your output format is ambiguous.
- You need the model to mimic a specific reasoning or writing style.
- You want to show a correct and incorrect pattern explicitly.

---

## 3. Plan then answer pattern

Ask the model to think first, then answer.

- Request a brief plan or reasoning step before the final result.
- Specify output format for both the plan and the answer.
- This is useful for decisions, complex reasoning, and multi-step tasks.

### Why it helps

- Forces the model to structure its thought process.
- Reduces rambling and improves decision quality.
- Creates a safe reasoning trail without overwhelming the final answer.

---

## 4. Data extractor pattern

Use strict JSON schema prompts for reliable parsing.

- Treat the task as extracting structured data from text.
- Define each field and data type explicitly.
- Tell the model to use `null` when a value is missing.
- Provide the application context: explain how the extracted data will be used.

### Example use cases

- Extract customer details from emails.
- Parse order info for a CRM.
- Build structured records from unstructured messages.

---

## 5. Router and classifier pattern

Branch workflows with confidence by categorizing input.

- Define a small set of mutually exclusive categories.
- Make categories easy to distinguish.
- Request category, confidence, and any supporting details.
- Output can be CSV, JSON, or table format.

### Best practices

- Keep class count low (3–6 categories).
- Avoid overlapping labels.
- Use this pattern for customer issue routing, content classification, and automation branching.

---

## 6. Summarizer with hard caps

Use strict length limits for dashboard and notification outputs.

- Specify maximum length, e.g., fewer than 18 words or 120 characters.
- Require critical information if present, such as dates or risk indicators.
- Ask for plain text summary when you need a short, display-ready sentence.

### Why it works

- Reduces output drift.
- Keeps summaries consistent across vendor guides.
- Ideal for status lines, one-line updates, and banner text.

---

## 7. Critic then revise pattern

Iterate the model’s output internally before delivering it.

- Generate an initial draft.
- Check it against an explicit rubric.
- Validate JSON schema and required fields.
- Revise the draft to incorporate corrections.

### When to use this

- Downstream automation breaks on malformed data.
- You need higher quality output without excessive API retries.
- You want the model to self-check and improve in the same prompt.

---

## 8. XML-tagged section pattern

Use XML-like tags to clearly separate prompt sections.

- Useful when prompts become long or messy.
- Recommended by Anthropic, Amazon Bedrock, and other vendors.
- Improves human readability and model instruction parsing.

### Benefit

- Creates strong boundaries between role, instructions, context, and data.
- Reduces instruction bleed and misinterpretation.

---

## 9. Tool/function caller pattern

Teach the model how and when to use external tools.

- List each available tool, its description, and example usage.
- Instruct the model to choose the right tool based on the request.
- Provide strict argument schemas for tool inputs.
- Use explicit parameter names and field definitions.

### Example

- A search tool should receive a concise search query.
- A send-email tool should receive `to`, `subject`, and `body` fields.
- A function caller prompt should tell the model when to use which tool.

---

## Recommended workflow

1. Start with the universal skeleton.
2. Add role and persona.
3. Use examples when format is unclear.
4. Apply plan-then-answer for complex tasks.
5. Use structured schema for extractors and tool calls.
6. Limit categories for routing.
7. Cap summaries strictly for dashboards.
8. Validate and revise outputs with a critic step.
9. Use XML-style sections when prompts get complex.

---

## Final note

These patterns make prompt engineering more systematic and automation-ready. Use them to reduce model unpredictability and make your n8n workflows easier to wire into production.
